# Trending Search

Сервис «Сейчас ищут». Топ поисковых запросов в реальном времени за окно последних 5 минут. Принимает события поиска из Kafka, отдаёт топ-N запросов по HTTP с задержкой < 1ms на p99.

## Старт

Требования: Docker Desktop, Go 1.26+, make.

```bash
make up                                       # kafka + app + prometheus + kafka-ui
go run ./scripts/load_producer -duration=30s  # наполнить окно событиями
curl -s http://localhost:8080/api/v1/trending | jq
```

После `make up` доступно:

- HTTP API: http://localhost:8080
- Prometheus: http://localhost:9090
- Kafka UI: http://localhost:8081

Конфигурация через переменные окружения (`internal/config/config.go`).
Дефолты: окно 5 минут, бакет 10 секунд, Space-Saving k=10000, snapshot interval 1 секунда.

```bash
make test         # unit + integration
make bench-baseline   # vegeta 5k RPS, 30 сек
make load-attack      # генерация трафика с 30% ботов
make down
```

## Контракт payload

В задании формат события не задан, поэтому он спроектирован под требования сервиса:

```json
{
  "event_id": "9b1a7f4e-...",
  "query": "iphone 15 pro",
  "user_id": "user-42",
  "session_id": "sess-abc",
  "timestamp": "2026-05-25T18:30:00Z"
}
```

Обоснование полей:

| Поле         | Обоснование                                                                                                                |
|--------------|----------------------------------------------------------------------------------------------------------------------------|
| `event_id`   | дедупликация на стороне Kafka consumer при retry/rebalance, идемпотентность                                                |
| `query`      | поисковый запрос, нормализуется (lowercase, схлопывание пробелов, trim)                                                    |
| `user_id`    | первичный идентификатор для дедупликации; блокирует накрутку от одного юзера                                               |
| `session_id` | fallback для гостей без `user_id`; должно быть одно из полей: user_id или session_id                                       |
| `timestamp`  | время события на стороне продюсера; используется для bucket-attribution и anti_style_filter (старше 5 минут отбрасывается) |

Валидация (`internal/domain/event.go`): query непустая, валидный UTF-8, ≤ 256 рун, 
есть один из идентификаторов, timestamp не в будущем и не старше 5 минут. 
Если невалидное будет дроп с метрикой `trending_events_consumed_total{status="dropped_validation"}`.

## Архитектура

Данные текут в одну сторону: события заходят через Kafka consumer, проходят пайплайн фильтров, 
складываются в окно счётчиков. Параллельно фоновая горутина раз в секунду снимает срез окна и 
публикует его в `atomic.Value`. HTTP API читает оттуда без локов.

### Поток одного события

Consumer забирает batch из топика `search.events` (3 партиции) 
и диспатчит сообщения на воркеры по числу партиций. Каждое сообщение проходит четыре стадии:

1. JSON + validate + normalize. 
Проверяется непустая query, валидный UTF-8, длина ≤ 256 рун, наличие `user_id` или `session_id`, 
timestamp не в будущем и не старше 5 минут. 
Query нормализуется. Если невалидное дропается с метрикой `dropped_validation`.

2. Dedup через Bloom filter с ротацией. 
Ключ: `u:userID|query` или `s:sessionID|query` для гостей. 
Деупликатор держит 3 фильтра одновременно, ротирует их каждые 10 секунд, 
поэтому эффективное окно дедупа — 30 секунд. 
На каждый запрос проверяем все 3 фильтра (если уже видели - дропаем), пишем в текущий. 
Повтор от одного юзера в 30-секундном окне отсекается.

3. Anomaly detection через EWMA.
Для каждой query держится скользящее среднее частоты появлений (alpha=0.3). 
Если текущая частота в 5+ раз превышает baseline и query живёт уже ≥ 60 секунд, то 
query помечается флагом anomaly. На этой стадии событие не дропается,
флаг используется позже при ранжировании.

4. Window.Add: событие попадает в bucket по формуле `floor(timestamp / 10s)` 
и инкрементирует Space-Saving счётчик внутри этого bucket'а.
Если timestamp лежит вне 5-минутного окна, то дроп. Окно состоит из 30 бакетов по 10 секунд каждый.

### Хранение: bucketed sliding window

Окно — массив из 30 `SpaceSaving` структур, по одной на бакет. Space-Saving - алгоритм для приближённого top-K с фиксированной памятью (k=10000 слотов): частые query сохраняют точные счётчики, редкие вытесняются и накапливают error-bound. Это даёт O(1) Add и O(k) для сборки топа.

Бакеты вращаются по кругу: каждые 10 секунд старший становится новым и обнуляется. Каждый бакет защищён собственным mutex, что даёт: события одного 10-секундного слота конкурируют только за свой бакет, а разные слоты идут параллельно.

### Чтение: snapshot pattern

Фоновая горутина раз в секунду собирает срез:

1. Снимает RLock на window, лочит каждый бакет по очереди, мержит их `SpaceSaving` в один большой (через `AddN` — bulk-инкремент за O(уникальных query)).
2. Применяет penalty для query, помеченных как anomaly: `count *= 0.1`.
3. Фильтрует query из stop-list.
4. Сортирует, отрезает топ-1000, кладёт в `atomic.Value` одним `Store`.

API-обработчик `GET /api/v1/trending?limit=N` делает `value.Load()` - это атомарная операция и режет до запрошенного limit.

### Защита от накруток: три слоя

Все три механизма работают одновременно, каждый ловит свой сценарий:

- **Bloom filter** - спам от одного юзера. Стоимость 127 ns/op, 0 allocs.
- **Space-Saving + bucketed window** - естественный счётчик. Тот, кто чаще встречается за 5 минут будет выше в топе. Алгоритм гарантирует точность для всего, что выше `N/k = 10/10000`, то есть для любого query с count > 0.1% от потока. Хвост может быть слегка завышен из-за error-bound, но в топ он всё равно не попадает.
- **EWMA anomaly detection** - координированная атака от множества «юзеров», которая обходит Bloom (разные user_id). EWMA замечает резкий всплеск частоты query, ставит флаг, snapshot builder применяет penalty при ранжировании. Stoимость 26 ns/op в hot path.

### Конфигурация

Все параметры выносятся в env-переменные (см. `internal/config/config.go`). 
Дефолты подобраны под задание: окно 5 минут, bucket 10 секунд, Space-Saving k=10000, 
snapshot interval 1 секунда, dedup window 30 секунд. Меняются без пересборки.

## Trade-offs

| решение | trade-off                                                                                                                                                                                       |
|---|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Окно как 30 × 10s бакетов | Точность по времени 10 секунд. Если событие пришло на 11:00:00.001, оно попадёт в один бакет с событиями 10:59:50.999.                                                                          |
| `atomic.Value` snapshot, билд раз в секунду | API может вернуть данные на 1 секунду свежее реальности. Можно было, например, лочить и считать на каждом запросе, но это убьёт latency.                                                        |
| Bloom filter | Один процент уникальных событий ошибочно сочтутся повторами и отвалятся. Это меньше шума, чем накрутка.                                                                                         |
| Space-Saving | Точность гарантирована только для запросов с count > N/k. Хвост (редкие query) может иметь завышенный count из-за error-bound. Для топа это не критично - нас интересует именно вершина.        |
| Anomaly soft penalty (count *= 0.1) вместо drop | Органика, попавшая под флаг по совпадению, не теряется полностью — она восстановится, когда EWMA-baseline догонит реальный тренд. Но фейковый тренд получит 10% от своего веса в топе, а не 0%. |
| MinAge=60s в anomaly | Первые 60 секунд после старта приложения anomaly не делает флаги, чтобы не штрафовать новые запросы на холодном старте. Поэтому атака, начатая в первую минуту, проскочит.                      |
| Dedup window 30 секунд | Медленный спам (1 раз в минуту от одного юзера) не отловится. Расчёт на то, что такой темп не повлияет на топ.                                                                                  |

## Проблемы исходной постановки

В ТЗ есть несколько недоопределённых мест. Решения, принятые в проекте:

1. **Формат payload не задан**, был спроектирован самостоятельно (см. выше). Ключевое решение — `session_id` как fallback к `user_id`.
2. **«5 минут» — какая точность?** Принято примерно 10 секунд через размер бакета.
3. **«Аномальные всплески» определены размыто.** Реализовано три слоя защиты: Bloom, Space-Saving, EWMA anomaly.
4. **Гости без `user_id`** → fallback на `session_id`. Если оба пустые - drop.
5. **Аномалию дропать или показывать с пометкой?** soft penalty. Пользователи всё равно ищут что-то trending, и если это совпало с EWMA-всплеском по уважительной причине (новость, релиз), резкий drop сделает топ менее полезным. .

## HTTP API
GET  /api/v1/trending[?limit=N]     топ-N запросов, default 100, max 1000

GET  /api/v1/stoplist             текущий стоп-лист

POST /api/v1/stoplist             добавить слово ({"word": "..."})

DEL  /api/v1/stoplist/{word}      удалить слово

GET  /healthz                     liveness

GET  /readyz                      readiness

GET  /metrics                     Prometheus

Пример:

```bash
$ curl -s http://localhost:8080/api/v1/trending?limit=3 | jq
{
  "data": [
    {"query": "iphone 15", "count": 1247},
    {"query": "airpods", "count": 892},
    {"query": "samsung s24", "count": 651}
  ]
}
```

## Результаты бенчмарков

На MacBook Pro M2 Pro, vegeta + Docker Desktop:

| сценарий | RPS | p50 | p90 | p99 | success |
|---|---|---|---|---|---|
| baseline | 5000 | 226 µs | 311 µs | 871 µs | 100% |
| stress | 10000 | 268 µs | 423 µs | 1.10 ms | 100% |
| attack (5k API + 2k Kafka, 30% ботов) | 5000 | 233 µs | 375 µs | 1.36 ms | 100% |


- 10k RPS является потолком измерений, но не приложения. 
На 10k RPS приложение отвечает за < 0.3ms, то есть загружено меньше чем на 1%.
- Параллельная Kafka-нагрузка с ботами не сдвигает p50/p90 API. Lock-free `atomic.Value` snapshot 
изолирует читателей от писательской нагрузки.
- Стоимость одного события end-to-end примерно равно 2-3 µs,
то есть один CPU-поток способен работать с 300-500k событиями в секунду. 
HTTP-чтение из `atomic.Value` занимает наносекунды плюс JSON-маршалинг. 
На production-RPS сервис работает с большим запасом.
